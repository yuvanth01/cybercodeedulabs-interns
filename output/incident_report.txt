### 3. Root Cause Analysis
The incident was a targeted attempt to exploit common SSH vulnerabilities. The attacker utilized automated scripts to conduct a dictionary-based password attack against the root user account. The root cause of the attempt is the exposure of the SSH service to the internal network, combined with a lack of rate-limiting or account lockout policies on the target host, which allowed the attacker to persist in their efforts until the firewall threshold was met.

### 4. Evidence Collected
* Authentication Logs: 150 failed SSH login attempts recorded in the /var/log/auth.log file.
* Behavioral Evidence: Sustained sequence of login requests occurring within a narrow 5-minute window.
* Administrative Target: Documentation of multiple failed attempts to access the "root" account, indicating a goal of full system compromise.
* Network Evidence: Firewall logs confirming the successful drop of all traffic from 192.168.1.100.

### 5. Business Impact
The potential impact of this attack was high, as a successful compromise of the root account would have granted the attacker complete control over the Ubuntu Server, potentially leading to unauthorized data access, system modification, or lateral movement within the network. However, due to effective defensive configurations, there was no actual compromise, no data exfiltration, and no service downtime experienced by the business.

### 7. Recommendations
* Disable Root Login: Modify the sshd_config file to set 'PermitRootLogin no' to prevent direct root access.
* Implement Key-Based Authentication: Transition from password-based SSH authentication to SSH keys and disable password authentication entirely.
* Deploy Fail2Ban: Install and configure Fail2Ban to automatically ban IPs after a set number of failed login attempts, adding a secondary layer of protection.
* Change Default Port: Move the SSH service from the default Port 22 to a non-standard port to reduce exposure to automated scanners.
* Enhance Monitoring: Configure real-time alerts for failed login attempts to be sent directly to the SOC dashboard for faster response times.

### 8. Conclusion
The incident was a standard automated brute-force attempt that was successfully mitigated by our perimeter security defenses. While the system remained secure, this incident highlights the need for a "defense-in-depth" approach. By implementing the recommended hardening steps, we will significantly increase the security posture of the Ubuntu Server and minimize the risk of future credential-based attacks. The incident is considered closed.
